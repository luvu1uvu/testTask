# План реализации — трекер рисков проекта

Согласован с пользователем 2026-08-15 в сессии 5 (`sessions/session-5.md`).
Основа — `SPEC.md` и Часть II `AGENTS.md`. Планировочная сессия реализацию не
начинала; каждый шаг ниже выполняется отдельной будущей сессией.

Вне этого плана: `README.md` с итоговым отчётом, сравнение `naive-run/` с
итоговой реализацией, независимый аудит — отдельные последующие этапы после
выполнения всех семи шагов.

## Порядок выполнения каждого шага

Общий для всех шагов ниже, не повторяется в каждом шаге отдельно.

1. Шаг выполняется в отдельной сессии и отдельным вызовом агента.
2. Файл сессии (`sessions/session-N.md`) создаётся до первой содержательной
   правки.
3. Промпты записываются в журнал дословно, сразу при получении.
4. Перед началом работы агент повторяет своё понимание шага и критерий
   «готово, когда…» — и только после этого правит файлы.
5. Изменяются только файлы, перечисленные в шаге плана.
6. Размышления, принятые решения и использованные инструменты фиксируются в
   журнале по ходу работы — независимо от того, будет ли результат в итоге
   принят.
7. Пользователь принимает или отклоняет результат по записанному критерию
   «готово, когда…».
8. Если пользователь отклонил результат, журнал сессии всё равно сохраняет
   выполненную работу и явно зафиксированную причину отказа — запись не
   переписывается и не удаляется задним числом.
9. Только после приёмки шага обновляются: статус шага в этом `PLAN.md`,
   финальный вердикт сессии в журнале и `sessions/STATE.md`.
10. После этого принятый шаг фиксируется отдельным логически завершённым
    коммитом.
11. Непринятый шаг не отмечается завершённым; доработка выполняется в рамках
    той же задачи новым вызовом агента.
12. После финального коммита сессии её файлы больше не изменяются.

### Шаг 1 — Модель риска, расчёты и валидация

**Цель:** зафиксировать форму данных риска и все чистые функции над ней, без
DOM и localStorage.

**Файлы:** `js/risk-model.js` (новый), `tests.html` (новый, каркас раннера),
`js/tests/risk-model.test.js` (новый).

**Входит:**
- модель риска: `{ id, title, description, probability, impact, measure, responsible, status, createdAt, updatedAt }`; `probability`/`impact` — числа 1–5; даты — ISO-строки; **балл и приоритет не хранятся** — только вычисляются функциями из `probability`/`impact`;
- статус хранится как один из пяти **стабильных внутренних кодов**:
  `open`, `in_progress`, `monitoring`, `realized`, `closed`;
- единая таблица соответствия кодов русским подписям в `risk-model.js`
  (экспортируется, используется интерфейсом для отображения):

  | код | подпись |
  |---|---|
  | `open` | «Открыт» |
  | `in_progress` | «В работе» |
  | `monitoring` | «Под наблюдением» |
  | `realized` | «Реализовался» |
  | `closed` | «Закрыт» |

  Причина: `SPEC.md` исключает локализацию только из v1, а не навсегда;
  внутренний формат данных не должен зависеть от текста интерфейса. Это также
  соответствует соглашению `AGENTS.md` «имена переменных, функций и данных в
  коде — на английском».
- валидация модели принимает **только** пять перечисленных кодов как значение
  статуса (русские подписи как значение статуса — невалидны);
- фабрика создания риска: генерирует стабильный уникальный `id`
  (`crypto.randomUUID()` — нативный Web Crypto API, не внешняя библиотека),
  проставляет `createdAt = updatedAt = текущее время в ISO`, статус по
  умолчанию `open`;
- расчёт балла (`probability × impact`) и уровня приоритета по границам;
- компаратор сортировки: балл ↓, затем влияние ↓, затем `createdAt` ↓ (более
  новый выше);
- валидация полей: длины с учётом trim, «только пробелы» = пусто,
  допустимость 1–5, обязательность меры/ответственного при статусе
  `in_progress`.

**Не входит:** DOM, localStorage, рендеринг, сохранение.

**Готово, когда:** `tests.html` (через `python3 -m http.server`) зелёный по
всем тестам модуля, включая: балл 25/«Критический», границы 4/5/9/10/15/16;
ровно 5 допустимых кодов статуса, русская строка вместо кода отклоняется
валидацией; таблица код↔подпись покрывает все 5 значений в обе стороны;
**1000 последовательно созданных фабрикой рисков получают 1000 уникальных
`id`**; сортировка корректно разводит равный балл по влиянию, затем по
`createdAt`; фабрика ставит статус `open` и совпадающие `createdAt`/`updatedAt`
в ISO; объект риска не содержит полей балла/приоритета.

**Закрывает критерии SPEC (на уровне модульных тестов, до UI):** балл/границы
приоритета; правило сортировки по умолчанию; длины полей и «пробелы = пусто»;
допустимость только 1–5; обязательность меры/ответственного для статуса
«в работе»; основа для «два одинаковых названия — отдельные записи»
(уникальность по `id`, не по названию).

**Проверка перед приёмкой:** полный вывод `tests.html` (список пройденных/
упавших проверок).

### Шаг 2 — Хранение данных

**Цель:** persist-слой поверх модели из шага 1, с версионированием и
безопасной реакцией на повреждённые данные.

**Файлы:** `js/storage.js` (новый), `js/tests/storage.test.js` (новый),
правки в `tests.html`.

**Входит:**
- продакшн-ключ `project-risk-tracker:v1`; формат значения
  `{ version: 1, risks: [...] }`; в `risks` каждый риск хранит статус
  внутренним кодом (шаг 1), не русской подписью;
- функции чтения/записи/CRUD (`load`, `save`, `addRisk`, `updateRisk`,
  `deleteRisk`, `getAll`) — каждая принимает необязательный параметр ключа
  хранения, по умолчанию равный продакшн-ключу;
- при обновлении риска обновляется только `updatedAt`, `createdAt`
  сохраняется;
- **атомарная проверка повреждённых данных, без частичного восстановления**:
  неподдерживаемая версия (`version !== 1` или отсутствует), непарсящийся
  JSON, отсутствие/неверный тип `risks`, либо хотя бы **одна** запись не
  проходит валидацию модели из шага 1 (включая недопустимый код статуса,
  `probability`/`impact` вне 1–5) — весь набор данных считается повреждённым
  целиком; частичное восстановление отдельных записей не выполняется
  (согласовано, восстановление вне v1 по `SPEC.md`);
- явная функция сброса — вызывается только по прямому действию вызывающего
  кода, не автоматически при обнаружении повреждения.

**Изоляция тестов (обязательное требование):** тесты `storage.js` **всегда**
передают отдельный тестовый ключ (например, `project-risk-tracker:v1:test`),
никогда не читают/не пишут/не очищают продакшн-ключ; после каждого теста
тестовый ключ удаляется через `localStorage.removeItem`.

**Не входит:** UI, диалоги подтверждения, отображение сообщений об ошибке.

**Готово, когда:** тесты `storage.js` зелёные, включая: round-trip записи/
чтения; неподдерживаемая версия, битый JSON и запись с недопустимым кодом
статуса — все три дают «повреждено», не тихий пустой реестр; ручная проверка
в консоли браузера — до и после прогона `tests.html` продакшн-ключ
`project-risk-tracker:v1` не создан/не изменён.

**Закрывает критерии SPEC (частично, на уровне данных):** персистентность
после перезагрузки (round-trip); обнаружение повреждённых/неподдерживаемых
данных без автоматической перезаписи; два риска с одинаковым названием —
отдельные записи (хранение по `id`).

**Проверка перед приёмкой:** вывод `tests.html`; консоль браузера — явная
проверка, что продакшн-ключ не тронут тестами; ручной сценарий с намеренно
испорченным продакшн-ключом → функция чтения сообщает «повреждено», не
удаляя его сама.

### Шаг 3 — Каркас страницы и список рисков

**Цель:** статическая структура страницы и отображение реестра (без формы
создания).

**Файлы:** `index.html` (новый), `css/styles.css` (новый),
`js/ui/risk-list.js` (новый), `js/app.js` (новый, точка входа).

**Входит:** HTML-скелет, подключение модулей `type="module"`, рендер списка
рисков из `storage.js` с сортировкой и баллом/приоритетом, вычисленными на
лету через `risk-model.js`; статус риска отображается **русской подписью**
через таблицу код↔подпись из `risk-model.js`, а не внутренним кодом; метка
приоритета текстом + цветом; состояние «пустой реестр при первом запуске»
(сообщение + кнопка «Добавить первый риск», обработчик появится в шаге 4);
показ по умолчанию только активных статусов (`open`, `in_progress`,
`monitoring`); предупреждение о локальном хранении.

**Не входит:** форма создания/редактирования, переключатель фильтра,
удаление, обработка повреждённых данных в UI.

**Готово, когда:** страница открывается через `python3 -m http.server`;
риски, добавленные вручную через `storage.js` в консоли браузера,
отображаются отсортированными, с верными русскими подписями статуса и
метками приоритета; при пустом хранилище видно сообщение и кнопку.

**Закрывает критерии SPEC:** отображение сортировки по умолчанию (полностью);
метка приоритета текстом и цветом (полностью); предупреждение о локальном
хранении (полностью); пустой реестр при первом запуске (частично — кнопка
пока не ведёт к форме).

**Проверка перед приёмкой:** живой просмотр пустого состояния и состояния с
временными данными (внесены через консоль); проверка консоли браузера на
ошибки.

### Шаг 4 — Форма создания и редактирования риска

**Цель:** полный цикл создания/редактирования с валидацией в интерфейсе (без
управления статусом — оно в шаге 5).

**Файлы:** `js/ui/risk-form.js` (новый), правки `index.html`,
`css/styles.css`, `js/app.js`, правка кнопки «Добавить первый риск» из
шага 3.

**Входит:** форма (название/описание/select вероятности/select
влияния/мера/ответственный), сообщения об ошибках у конкретных полей,
сохранение введённых данных при ошибке, фокус на первое некорректное поле,
пересчёт балла/приоритета и позиции в списке при редактировании; создание —
статус всегда внутренний код `open` (ставит фабрика из шага 1, на странице
отображается как «Открыт» через таблицу подписей); **изменение только текста
меры реагирования не меняет статус риска** — форма на этом шаге вообще не
содержит элемента смены статуса.

**Не входит:** смена статуса, удаление, фильтр по статусу.

**Готово, когда:** можно создать риск через UI с первого запуска (кнопка из
шага 3 работает), отредактировать существующий; блокировка сохранения при
пустых/некорректных полях с сообщением у нужного поля и сохранённым вводом;
правка меры реагирования у существующего риска не меняет его статус (код в
хранилище тот же).

**Закрывает критерии SPEC:** пустой реестр при первом запуске (полностью);
блокировка сохранения без обязательных полей (сообщения/фокус/сохранённый
ввод); длины полей и «пробелы = пусто» в UI; выбор вероятности/влияния только
1–5 через select; пересчёт балла/приоритета и позиции при редактировании; два
риска с одинаковым названием сохраняются как разные записи (через реальный
UI).

**Проверка перед приёмкой:** живая проверка — создание, попытка сохранить с
пустыми полями, редактирование вероятности/влияния с проверкой пересчёта,
правка меры без смены статуса; консоль без ошибок; перезагрузка страницы
подтверждает сохранность.

### Шаг 5 — Статусы и фильтр по статусу

**Цель:** ручной перевод риска между всеми пятью статусами через форму
редактирования и фильтрация реестра.

**Файлы:** правки `js/ui/risk-form.js` (добавляется элемент выбора статуса,
заполняемый русскими подписями из таблицы код↔подпись, и его валидация),
новый `js/ui/filters.js` (работает с внутренними кодами статуса, отображает
русские подписи), правки `js/ui/risk-list.js` (рендерит то, что отдаёт
`filters.js`), правки `index.html`, `css/styles.css`.

**Входит:** элемент смены статуса в `risk-form.js` (список из пяти русских
подписей, за которыми стоят внутренние коды); блокировка перевода в
`in_progress` без меры/ответственного с сообщениями у полей; фильтр по
статусу в `filters.js` (по умолчанию активные: `open`/`in_progress`/
`monitoring`; возможность показать `closed`/`realized`); закрытые/
реализовавшиеся риски, найденные через фильтр, открываются на редактирование
в том же `risk-form.js` из шага 4; отдельное состояние «нет рисков по
текущему фильтру» (сообщение + «Сбросить фильтры») — **отличается от
состояния полностью пустого реестра**: кнопки «Добавить первый риск» здесь
нет.

**Не входит:** удаление риска, обработка повреждённых данных.

**Готово, когда:** риск переводится вручную в любой из 5 статусов; `closed`/
`realized` пропадают из списка по умолчанию, но видны и редактируемы через
фильтр; система не меняет статус сама; перевод в `in_progress` без
меры/ответственного блокируется; пустой результат фильтра показывает нужное
сообщение (без кнопки «Добавить первый риск») и сбрасывается кнопкой
«Сбросить фильтры».

**Закрывает критерии SPEC:** перевод в каждый из 5 статусов; скрытие
закрытых/реализовавшихся из активного списка при сохранении в хранилище и
доступности через фильтр; отсутствие автозакрытия; блокировка перехода в «в
работе» без меры/ответственного; фильтр по умолчанию только активных
статусов; отдельное сообщение и кнопка сброса при пустом результате фильтра.

**Проверка перед приёмкой:** живая проверка всех 5 переходов; проверка
блокировки перехода в «в работе»; проверка, что найденный через фильтр
закрытый риск открывается на редактирование; проверка пустого результата
фильтра и его отличия от пустого реестра; консоль без ошибок.

### Шаг 6 — Удаление и обработка повреждённых данных

**Цель:** безопасное удаление с подтверждением, сохранение текущего фильтра
после удаления, корректная реакция на нечитаемые данные при запуске.

**Файлы:** новый `js/ui/dialogs.js` (диалог подтверждения удаления), новый
`js/ui/data-error.js` (экран повреждённых данных при старте), правки
`js/ui/risk-list.js`, `index.html`, `css/styles.css`, `js/app.js`.

**Входит:** диалог подтверждения с названием риска и текстом о необратимости,
визуально опасная кнопка подтверждения; после удаления — **текущий активный
фильтр сохраняется** (не сбрасывается на дефолтный); если после удаления
отфильтрованный список пуст, но в хранилище остались риски других статусов —
показывается состояние «пустой результат фильтра» из шага 5, а не «пустой
реестр»; состояние «пустой реестр» (переиспользует шаг 3/4) показывается
только когда удалён действительно последний риск во всём хранилище;
UI-обработка повреждённых данных при загрузке — сообщение + кнопка «Сбросить
данные и начать заново» с отдельным подтверждением через `dialogs.js`.

**Не входит:** изменения в форме создания/редактирования и в логике статусов
из шагов 4–5.

**Готово, когда:** удаление требует подтверждения; отмена ничего не меняет;
подтверждение удаляет риск из UI и `localStorage`; фильтр после удаления тот
же, что был до; удаление последнего риска внутри фильтра при непустом
хранилище показывает «пустой результат фильтра», а не «пустой реестр»;
удаление действительно последнего риска в хранилище показывает «пустой
реестр»; при испорченных данных в `localStorage` при открытии страницы
показано сообщение и кнопка сброса, сброс требует отдельного подтверждения.

**Закрывает критерии SPEC:** удаление с подтверждением (название +
предупреждение о необратимости, «Отмена»/«Удалить»); сохранение фильтров
после удаления; пустой реестр после удаления действительно последнего риска;
обработка повреждённых/неподдерживаемых данных в интерфейсе без
автоматической перезаписи, с явным подтверждением сброса.

**Проверка перед приёмкой:** живая проверка удаления (отмена и подтверждение)
с активным нестандартным фильтром — фильтр не сбросился; проверка различия
«пустой фильтр» vs «пустой реестр»; проверка сценария с вручную испорченным
`localStorage`; консоль без ошибок.

### Шаг 7 — Финальная комплексная проверка

**Цель:** сквозная проверка готового приложения по полному чек-листу, **без
изменения кода приложения**.

**Файлы:** код приложения не изменяется вообще. Создаются только:
`evidence/final-verification.md`, `evidence/tests-html-result.png`,
`evidence/main-scenario.png`, `evidence/edge-case-scenario.png`,
`evidence/performance-200-risks.png`; обязательно обновляется
`sessions/STATE.md`.

**Входит:** прогон `tests.html` целиком с полным выводом; запуск через
`python3 -m http.server`; проверка основного сценария и минимум одного
нештатного (выбирается на этапе выполнения шага, фиксируется в
`evidence/final-verification.md`, какой именно); заполнение реестра ~200
записями и замер времени открытия/фильтрации/сортировки (не более 1 секунды);
проверка консоли на ошибки; перезагрузка страницы с подтверждением
сохранности данных; повторная проверка повреждённых данных; прохождение всех
пунктов «Критерии приёмки» `SPEC.md` по списку с явной отметкой «пройден/не
пройден» и фактическим результатом по каждому в
`evidence/final-verification.md`; прохождение чек-листа «Что проверить перед
финальным ответом» из `AGENTS.md`. Все данные на скриншотах — вымышленные (не
реальные проекты/люди пользователя).

**Не входит:** README.md, сравнение с `naive-run/`, независимый аудит —
отдельные последующие этапы.

**Правило при найденном дефекте:** шаг **не** правит код. Дефект фиксируется в
`evidence/final-verification.md` как «не пройден» с фактическим результатом,
шаг в целом считается непройденным. Исправление — отдельная задача в
отдельной следующей сессии; после исправления шаг 7 перезапускается
**целиком заново**, а не только по упавшему пункту. Если исправление требует
изменить ожидаемое поведение или сам критерий приёмки — это отдельный вопрос
пользователю, не решение внутри шага 7.

**Готово, когда:** каждый пункт «Критерии приёмки» `SPEC.md` явно отмечен в
`evidence/final-verification.md` как пройден или не пройден (без формулировки
«всё готово» при наличии провалов); производительность на 200 записях
подтверждена измерением; все 5 файлов `evidence/*` созданы.

**Закрывает критерии SPEC:** весь чек-лист целиком, включая производительность
на ~200 записях.

**Проверка перед приёмкой:** содержимое `evidence/final-verification.md`
целиком, все 4 скриншота, полный вывод `tests.html`.
