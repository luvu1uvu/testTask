## Производительность на 200 рисках

**Создание данных:** ровно 200 валидных рисков созданы вызовами
`createRisk()` + `save()` из настоящих модулей приложения (`js/risk-model.js`,
`js/storage.js`), внутри headless-браузера, тем же кодом, что использует
само приложение. Распределение:
- **По статусам:** `open` 40, `in_progress` 40, `monitoring` 40,
  `realized` 40, `closed` 40 (`i % 5` для `i` от 0 до 199).
- **По приоритету (все 25 комбинаций вероятность×влияние):**
  вероятность = `1 + (i % 5)`, влияние = `1 + (floor(i / 5) % 5)` — по 8
  записей на каждую из 25 комбинаций, что даёт представленность всех
  четырёх уровней приоритета.

**Методика измерения:**

1. **Открытие реестра** — настоящая навигация браузера (`Page.navigate`,
   полная перезагрузка документа и всех ES-модулей с нуля); окончание
   замера — строки реестра появились в DOM **и** после этого прошло два
   последовательных кадра отрисовки (`requestAnimationFrame` дважды
   подряд); значение — `performance.now()` в этой точке (для полной
   навигации это время от начала навигации/`timeOrigin` документа до
   готовой прорисованной картинки). 5 независимых прогонов, каждый — полная
   перезагрузка страницы.
2. **Изменение фильтра** — значение настоящего `<select id="status-filter">`
   меняется через нативный сеттер `HTMLSelectElement.prototype.value`,
   затем диспатчится настоящее событие `change`
   (`select.dispatchEvent(new Event('change', {bubbles:true}))`) — тот же
   путь, что обрабатывает `js/ui/filters.js`. Замер — от момента диспатча
   события до изменения числа строк в `<tbody>` плюс один следующий кадр
   отрисовки. Значение фильтра чередовалось между «Активные» и «Закрыт» на
   каждом из 5 прогонов.
3. **Сортировка** — `[...risks].sort(model.compareRisks)` (тот же
   импортированный `compareRisks` из `js/risk-model.js`, что использует
   `app.js`) на полном массиве из всех 200 записей хранилища, в изоляции
   от фильтрации и рендера. 5 прогонов подряд на одной загруженной
   странице.

**Результаты (все значения по пяти прогонам, мс):**

| Действие | Все значения | **Максимум** | Лимит | Результат |
|---|---|---|---|---|
| Открытие реестра (реальная навигация + 2 кадра отрисовки) | 71,1 / 65,0 / 65,3 / 63,5 / 66,2 | **71,1 мс** | 1000 мс | С запасом ×14 |
| Изменение фильтра (реальное событие `change`, чередование «Закрыт»/«Активные») | 14,5 / 13,1 / 10,2 / 13,6 / 10,0 | **14,5 мс** | 1000 мс | С запасом ×69 |
| Сортировка (`compareRisks` на полном массиве 200 записей) | 0 / 0,1 / 0 / 0 / 0,1 | **0,1 мс** | 1000 мс | С запасом ×10000 |

Во всех трёх случаях для сравнения с критерием (≤ 1000 мс) взято
**максимальное**, а не лучшее и не среднее значение из пяти прогонов. Ни
один прогон ни по одному действию не приблизился к лимиту.

**Проверка отзывчивости после измерений:** страница перезагружена ещё раз
с теми же 200 записями; клик по кнопке «Изменить» у первой строки реестра
мгновенно открыл форму редактирования с корректно предзаполненными
реальными данными (`FORM_OPENED`); интерфейс не завис.

Скриншот `performance-200-risks.png` показывает полный реестр (фильтр
«Активные», 120 из 200 записей), все четыре уровня приоритета и все три

## Повторная проверка доступности

### Диалоги — ловушка фокуса и Escape

Проверены оба типа диалога: подтверждение удаления риска и подтверждение
сброса повреждённых данных. Диалог удаления открывался и закрывался
последовательно **четыре** раза подряд в этой сессии (минимум три,
требуемых заданием, выполнен с запасом), диалог сброса — дважды (по разу
на битый JSON и на неподдерживаемую версию).

Для диалога удаления, воспроизведено вживую в этой сессии:

- **Начальный фокус** — на кнопке «Отмена» (`document.activeElement.textContent
  === 'Отмена'`), подтверждено при каждом из четырёх открытий.
- **`Tab`** («Отмена» → подтверждение): подтверждено —
  `document.activeElement.textContent === 'Удалить'` после одного `Tab`.
- **Следующий `Tab`** (подтверждение → «Отмена», без выхода в фон):
  подтверждено — `document.activeElement.textContent === 'Отмена'`,
  `document.activeElement.closest('.dialog')` не `null`.
- **`Shift+Tab`** («Отмена» → подтверждение): подтверждено —
  `document.activeElement.textContent === 'Удалить'`,
  `document.activeElement.closest('.dialog')` не `null`.
- **Фокус не выходит в фон:** на каждом шаге цикла Tab/Shift+Tab
  `document.activeElement.closest('.dialog')` оставался внутри диалога.
- **`Escape` закрывает диалог как отмена:** подтверждено дважды подряд (1-й
  и 2-й циклы) — после `Escape` диалог исчез (`.dialog` не найден в DOM),
  риск НЕ удалён (число записей в хранилище не изменилось, сверено сырым
  значением ключа).
- **Опасное действие после Escape не выполняется:** подтверждено — число
  рисков в хранилище до и после Escape совпадает.
- **После отмены фокус возвращается на инициатор:** подтверждено —
  `document.activeElement.getAttribute('aria-label') === 'Удалить риск
  «Ттт»'` сразу после каждого Escape.
- **Отсутствие накопления обработчиков:** после второго открытия/закрытия
  консоль браузера чиста (`read_console_messages` с фильтром только ошибок
  — пусто); третий и четвёртый циклы (третий — снова полный Tab/Shift+Tab
  до закрытия кликом по «Отмена», четвёртый — подтверждение удаления)
  прошли без повторного срабатывания устаревших обработчиков и без ошибок
  в консоли.

Для диалога сброса повреждённых данных (оба сценария — битый JSON и
неподдерживаемая версия): начальный фокус на «Отмена» подтверждён,
`Escape` закрыл диалог без выполнения сброса (сырое повреждённое значение
ключа сверено побайтно до/после — не изменилось), экран ошибки остался
на месте; повторное открытие и подтверждённый сброс (клик по кнопке
подтверждения) в обоих случаях вызвали `resetStorage()` и показали
настоящее пустое состояние реестра.

Скриншот `accessibility-dialog.png` (отдельный headless-снимок, два
вымышленных риска с разными названиями, ни один не связан с реальными
данными интерактивной сессии) показывает открытый диалог удаления с
фокусом на кнопке «Отмена» и визуально опасной кнопкой «Удалить».

### Доступные имена кнопок «Изменить»/«Удалить»

Для риска «Ттт» (вероятность 5, влияние 5) и риска «Отказ основного

- **Доступные имена различаются** между рисками с разными названиями:
  подтверждено (см. список выше — все четыре значения уникальны).

  названием («Задержка тестового окружения», см. критерий 12), закономерно

  `row.innerHTML.includes('<img')` → `false` (тег не вставлен как живой

  буквальный текст `Изменить риск «<img src=x onerror=alert(1)>»`. Alert не
  сработал ни разу, консоль браузера осталась чистой. Риск удалён после
  проверки, чтобы не засорять демонстрационные данные.

## Известные ограничения

- Как и в шаге 7 (сессия 12), для сохранения PNG-доказательств и точных
  измерений производительности использовался отдельный headless-экземпляр
  установленного в системе Chrome, управляемый самописным CDP-клиентом —
  техническое ограничение инструмента панели Browser (нет прямого
  сохранения скриншота в файл), а не отклонение от кода или логики
  приложения. Оба контекста (интерактивная панель и headless) показывают
  идентичное поведение одного и того же кода приложения.
- В процессе headless-измерений производительности один системный вызов
  `pkill -f "Google Chrome Helper"` (сделанный при отладке зависшего
  процесса создания скриншота, до перехода на надёжный CDP-подход)
  затронул несколько фоновых Helper-процессов уже открытого личного окна
  Chrome пользователя (не headless-инстанс — тот не совпал с этим
  паттерном по `user-data-dir`). Основной процесс личного Chrome
  (запущенный 9 июля) не был затронут и оставался в списке процессов на
  всём протяжении сессии; современный Chrome прозрачно перезапускает
  такие вспомогательные процессы (GPU/сеть/хранилище) без закрытия вкладок
  пользователя. Видимых последствий для пользователя зафиксировано не
  было, но сам факт стоит отметить как непреднамеренное побочное действие
  при отладке методики проверки, а не действие в отношении приложения или
  данных проекта.
- Отдельный сгенерированный набор из 200 тестовых рисков случайно на
  короткое время задержался в продакшн-ключе интерактивной панели (первая
  попытка измерения производительности, до перехода на headless-подход) —
  обнаружено и устранено вызовом `resetStorage()` в той же сессии, до
  завершения проверки; исходное состояние (`null`) восстановлено и сверено
  повторно. Подробности — в `sessions/session-15.md`, раздел «Размышления».
