# Трекер рисков проекта

Локальное одностраничное веб-приложение для руководителя проекта: реестр
рисков, оценка по вероятности и влиянию, расчёт приоритета, отслеживание
мер реагирования. Один проект, один пользователь, данные хранятся только
в текущем браузере — совместной работы и синхронизации нет.

Тема выбрана в направлении Project/Product: ведение реестра рисков —
практическая задача планирования проекта и контроля его состояния, знакомая
по обычной работе руководителя проекта. Приложение сделано как учебный
проект для этого задания и пока не используется в реальной работе.

## Быстрый запуск

Из корня репозитория:

```bash
python3 -m http.server 8765
```

Затем открыть в браузере:

- приложение — [http://localhost:8765/](http://localhost:8765/)
- тесты — [http://localhost:8765/tests.html](http://localhost:8765/tests.html)

Остановить сервер — `Ctrl+C`.

Установка зависимостей не требуется — их нет. Нужны только Python 3 и
современный браузер. Открыть `index.html` напрямую через `file://` не
получится: приложение подключает JavaScript как ES-модули
(`type="module"`), а браузеры блокируют их загрузку с локального файла без
сервера.

## Что умеет

- Создание и редактирование риска: название, описание, вероятность,
  влияние, мера реагирования, ответственный.
- Вероятность и влияние — выбор из фиксированных значений 1–5, свободный
  ввод невозможен.
- Балл риска = вероятность × влияние, пересчитывается автоматически при
  изменении оценок.
- Четыре уровня приоритета с текстовой меткой и цветом.
- Пять статусов риска с ручным переводом между ними.
- Мера реагирования и ответственный становятся обязательными при переводе
  риска в статус «В работе».
- Сортировка реестра по убыванию балла с двумя тай-брейками (влияние,
  затем дата создания).
- Фильтр по статусу, включая режим «Активные» по умолчанию.
- Отдельные состояния для пустого реестра и пустого результата фильтра.
- Удаление риска с обязательным подтверждением, содержащим название риска.
- Сохранение данных в `localStorage`, переживающее перезагрузку страницы.
- Безопасная обработка повреждённых или неподдерживаемых данных — без
  автоматической потери информации.
- Клавиатурное управление диалогами: ловушка фокуса, закрытие по `Escape`.
- Безопасный вывод пользовательского текста (без исполнения HTML/скриптов
  в названии или описании риска).

## Как пользоваться

1. Добавить риск кнопкой «Добавить риск» (или «Добавить первый риск» на
   пустом реестре).
2. Заполнить обязательные поля: название, описание, вероятность, влияние.
3. Выбрать вероятность и влияние из списка 1–5 — балл и приоритет
   рассчитаются автоматически.
4. Сохранить риск.
5. При необходимости открыть риск на редактирование и назначить меру
   реагирования, ответственного и статус.
6. Использовать фильтр над реестром, чтобы увидеть риски по конкретному
   статусу, и редактирование — чтобы изменить оценки или статус.
7. Закрыть риск, отметить его реализовавшимся либо удалить — удаление
   требует отдельного подтверждения с названием риска.

## Модель приоритета и статусы

Балл риска = вероятность × влияние (оба поля — целые числа 1–5, диапазон
балла 1–25). Уровень приоритета определяется по баллу:

| Балл | Приоритет |
|---|---|
| 1–4 | Низкий |
| 5–9 | Средний |
| 10–15 | Высокий |
| 16–25 | Критический |

Риск может находиться в одном из пяти статусов, переключаемых вручную:
**Открыт** → **В работе** → **Под наблюдением** → **Реализовался** /
**Закрыт**. Переходы не обязаны идти строго по порядку — руководитель
выбирает статус сам, но система не переводит риск в другой статус
автоматически. Подробности — в [SPEC.md](SPEC.md).

## Хранение данных

- Данные хранятся только в `localStorage` текущего браузера — привязаны
  к конкретному браузеру, компьютеру и адресу (`origin`), на котором
  открыто приложение.
- Очистка хранилища браузера удалит все риски безвозвратно.
- Сервер (`python3 -m http.server`) ничего не отправляет и не хранит —
  он лишь раздаёт статические файлы.
- Резервное копирование, экспорт, импорт и синхронизация между
  устройствами не реализованы.
- Если сохранённые данные повреждены или не читаются, приложение не
  падает и не заменяет их молча — показывает сообщение об ошибке и
  предлагает явный сброс; без подтверждения пользователя данные не
  удаляются.

## Сравнение двух прогонов

Кроме итоговой реализации, в проекте сохранён результат **наивного
прогона** — тот же продукт, собранный одним коротким промптом без
спецификации и правил, в изолированной среде (`naive-run/`).

Итоговая реализация проходит **18 из 18** критериев приёмки `SPEC.md`.
Наивный прогон — **6 пройдено, 6 частично, 6 не пройдено** из тех же 18.

Наивная версия — рабочее и визуально насыщенное приложение: она
самостоятельно предложила ряд полезных идей сверх задания (матрицу рисков
5×5, поиск по названию, категории риска, экспорт/импорт данных), которых
нет в согласованной спецификации. Одновременно она без спецификации сама
придумала другую модель статусов (четыре вместо пяти, без «Реализовался»)
и другие границы приоритета. Самая существенная практическая проблема —
обработка повреждённых данных: наивная версия не сообщает об ошибке, а
молча показывает пустой реестр и при первом же следующем сохранении
**необратимо перезаписывает** повреждённые (но потенциально
восстановимые) данные без единого предупреждения.

Строгий процесс со спецификацией, пошаговой реализацией и независимым
аудитом потребовал значительно больше времени и сессий, чем один короткий
промпт, — но сделал поведение приложения предсказуемым, проверяемым и
согласованным с зафиксированными требованиями.

Подробности и полная таблица по всем 18 критериям —
[comparison/naive-vs-final.md](comparison/naive-vs-final.md). Скриншоты
для сравнения: [comparison/naive-run.png](comparison/naive-run.png),
[comparison/final-run.png](comparison/final-run.png).

## Что сознательно не сделано

Полный список — в разделе «Чего точно не делаем» [SPEC.md](SPEC.md).
Кратко:

- Несколько проектов одновременно, многопользовательский режим, роли и
  совместное редактирование.
- Серверное хранение, синхронизация между устройствами и авторизация.
- Управление инцидентами и последствиями реализовавшегося риска.
- История изменений и аудит предыдущих версий записи.
- Корзина и восстановление удалённых записей.
- Импорт и экспорт реестра.
- Уведомления, напоминания и интеграции с внешними системами.
- Комментарии, обсуждения и вложения.
- Аналитические дашборды, графики и отчёты.

## Допущения и известные ограничения

- Интерфейс, сообщения и тексты — только на русском языке.
- Ориентир объёма — до ~200 рисков; при этом объёме проверена
  производительность.
- Текстовые поля валидируются после `trim()` (строка из одних пробелов
  считается пустой, длина проверяется без краевых пробелов), но сами
  введённые пробелы по краям сохраняются как есть — это осознанно принятое
  поведение, а не дефект.
- Пользовательский интерфейс проверен вручную в реальном браузере;
  автоматические тесты (`tests.html`) покрывают только модель расчётов и
  хранилище данных, не UI-модули.
- Доступность проверялась клавиатурой (фокус, `Tab`, `Escape`) и через
  структуру DOM; отдельной проверки реальным экранным диктором не
  проводилось.
- Приложение не предназначено для хранения критичных данных без внешней
  резервной копии — резервного копирования и экспорта в нём нет.

## Процесс работы

Проект сделан по циклу «контекст → спецификация → наивный прогон → работа
по спецификации → проверка → аудит → отчёт», без пропуска этапов.

Сначала были согласованы правила работы (`AGENTS.md`) и написана
спецификация (`SPEC.md`) — до того, как появилась хотя бы одна строка кода
приложения. Отдельно, в изолированной среде без спецификации и правил,
сделан наивный прогон — его результат зафиксирован в `naive-run/` и с тех
пор не менялся.

Сама реализация велась по `PLAN.md` — семью последовательными шагами
(модель и валидация, хранение данных, каркас и список, форма, статусы и
фильтр, удаление и обработка повреждённых данных, финальная проверка),
каждый шаг — отдельная сессия с приёмкой по заранее записанному критерию
перед переходом к следующему.

После завершения всех шагов проведён независимый аудит: чистая сессия без
истории разработки проверила код и поведение приложения свежим взглядом.
Найденные находки доступности исправлены отдельной сессией и подтверждены
повторной полной проверкой всех 18 критериев приёмки. Последним шагом
исходный код сопоставлен с наивным прогоном по единой таблице критериев.

Полная хронология по сессиям — в [sessions/STATE.md](sessions/STATE.md).
