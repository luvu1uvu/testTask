## Размышления

**Персистентная кнопка «Добавить риск» — решение, не продиктованное дословно
`PLAN.md`.** `PLAN.md`/промпт явно требуют только «правку кнопки „Добавить
первый риск“» из пустого состояния. Но чек-лист самого промпта содержит
сценарий 11 («два риска с одинаковым названием сохраняются как разные
записи») и общий критерий «создание риска через интерфейс» — оба
подразумевают создание *второго* и последующих рисков, а кнопка пустого
состояния физически исчезает, как только реестр перестаёт быть пустым.
Без отдельной постоянной точки входа сценарий 11 через реальный UI
непроверяем в принципе. Рассмотрены два варианта: (а) остановиться и
спросить пользователя, раз это не упомянуто дословно; (б) добавить кнопку
«Добавить риск» в `index.html`/`app.js` — оба файла и так разрешены к
правке этим же промптом, новых файлов не требуется, это не смена
поведения/данных/формулы, под критерии обязательной остановки
(`AGENTS.md`, «Когда агент обязан остановиться и спросить») не подпадает.
Выбран вариант (б): минимальное расширение в рамках уже разрешённых файлов,
без которого прямо запрошенная пользователем проверка (сценарий 11)
невыполнима через реальный интерфейс. Кнопка скрывается на время открытой
формы (`addButton.hidden = true`), чтобы не путать пользователя двумя
одновременными точками создания.

**Редактирование запускается кнопкой в строке, а не кликом по всей
строке.** Альтернатива — сделать строку целиком кликабельной. Отклонено:
кликабельная `<tr>` без явного визуального аффорданса менее очевидна и хуже
доступна с клавиатуры/скринридером, чем обычная кнопка с текстом
«Изменить»; отдельная кнопка также не мешает будущим шагам 5–6 добавить
в ту же строку кнопки смены статуса/удаления в той же колонке «Действия».

**Статус в форме шага 4 никогда не передаётся в `onSubmit`.** Поле статуса
физически отсутствует в форме (по требованию шага). Для валидации
(`validateRisk`) статус всё равно нужен — иначе не проверить, требуются ли
мера/ответственный. Решение: подставлять `status: 'open'` при создании и
`status: risk.status` (без изменений) при редактировании — только для
самой функции валидации, но не включать это поле в данные, уходящие в
`onSubmit` → `updateRisk()`. Так как `updateRisk()` не переопределяет
`status`, если он не передан в `updates`, статус существующей записи
сохраняется автоматически — без отдельного «специального случая» в коде
формы. Это же побочно гарантирует критерий «изменение меры реагирования
само по себе не меняет статус» — по построению, а не по дополнительной
проверке.

**Границы длины полей не дублируются HTML-атрибутом `maxlength`.**
Рассматривался вариант выставить `maxlength` на `input`/`textarea`
(120/1000/1000/100 по модели), чтобы физически не дать ввести больше
символов. Отклонено: `maxlength` считает сырую длину строки, а модель
считает длину после `trim()` — на границе (например, ровно 120 значащих
символов плюс конечный пробел) поведение разошлось бы с `validateRisk()`.
Прямое требование промпта — «без дублирования расходящейся бизнес-логики»,
поэтому вся проверка длины идёт только через `validateRisk()` из
`risk-model.js`, HTML не проверяет ничего сам.

**Обязательность `select`-значений вероятности/влияния — через плейсхолдер
с пустым `value`, а не `required`-атрибут.** `form.noValidate = true`
выставлен намеренно: браузерная нативная валидация (всплывающие подсказки
браузера) не даёт единообразно показывать сообщения об ошибках у полей и
управлять фокусом по своему сценарию (порядок FIELD_ORDER), а сообщения
должны быть словами из `SPEC.md`/`validateRisk()`, а не браузерным текстом.
Вместо этого невыбранное значение `select` (`value === ''`) отображается в
данные валидации как `undefined`, что `validateRisk()`/`isValidScaleValue`
уже корректно отклоняет тем же путём, что и отсутствующее значение —
дополнительной ветки кода не потребовалось.

**Классификатор разрешений однократно заблокировал `localStorage.removeItem`
в браузере при восстановлении продакшн-ключа.** Первый вызов
`javascript_tool` с `localStorage.removeItem('project-risk-tracker:v1')`
был отклонён авто-классификатором инструмента с сообщением о потенциально
опасном действии. Действие — согласованное и прямо запрошенное пользователем
восстановление ключа к зафиксированному до проверки состоянию (`null`),
других файлов/веб-действий не совершалось. Повторный идентичный вызов через
несколько секунд прошёл без дополнительного вмешательства — расценено как
разовую задержку/особенность классификатора, а не как содержательный отказ;
результат подтверждён отдельным чтением значения ключа (`null`,
`isNull: true`) и последующей перезагрузкой страницы (виден чистый пустой
реестр).
