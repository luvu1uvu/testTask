### Раунд 2 — доработка по замечанию независимой проверки

Пользователь не принял первую версию: независимый ревьюер указал на реальный
пробел — `validateRisk()` была рассчитана только на данные формы (значения,
которые уже прошли через JS-объект с ожидаемыми ключами), но `storage.js` в
шаге 2 будет читать `JSON.parse()` произвольного содержимого `localStorage`
— там может оказаться `null`, строка, массив, объект без `id`, объект с
сохранённым `score`/`priority`, битые даты и т. д. Без отдельной функции
шаг 2 либо дублировал бы часть правил валидации у себя, либо строился бы на
функции, которая может бросить исключение на мусорном input. Согласен с
диагнозом: это действительно пробел в интерфейсе между шагами 1 и 2, а не
придирка к деталям реализации.

Решения, принятые при доработке:

- **`validateRisk()` не переписывалась с нуля** — добавлена только защитная
  проверка `isPlainObject` в начале функции (null/undefined/строка/массив ⇒
  сразу невалидный результат без исключения) и снята условность вокруг
  проверки статуса (`data.status !== undefined && ...` → всегда проверяется
  `isValidStatus(data.status)`). Это сознательно меняет поведение статуса:
  раньше отсутствующий статус считался допустимым (потому что форма шага 4
  ещё не содержит поле статуса), теперь — ошибка. Так как в явном
  требовании пользователя это прямо сформулировано («отсутствующий или
  неизвестный статус должен считаться ошибкой»), решение не требовало
  дополнительного уточнения; но стоит иметь в виду на шаге 4: при создании
  риска через форму `status: 'open'` нужно будет либо подставлять перед
  вызовом `validateRisk`, либо создавать риск через `createRisk()` (которая
  сама ставит `open`) до валидации остальных полей — как именно, решится
  в шаге 4.
- **`validateRiskRecord()` переиспользует `validateRisk()`**, а не дублирует
  правила длины/обязательности — вызывает её и сливает её `errors` с
  дополнительными проверками (`id`, тип строковых полей, ISO-даты,
  `updatedAt >= createdAt`, отсутствие `score`/`priority`). При слиянии
  ошибка типа поля (например, `title` — число) не перезаписывается более
  общим сообщением из `validateRisk` — иначе сообщение было бы вводящим в
  заблуждение («укажите название», хотя название есть, просто не строка).
- **Проверка ISO-дат — через раунд-трип, а не только regex.** Сначала
  проверяется формат строки регулярным выражением, затем — что
  `new Date(...).toISOString()` возвращает ровно исходную строку. Это
  отсекает синтаксически похожие, но не существующие даты (например,
  `2026-02-30T00:00:00.000Z`) независимо от того, как конкретный движок
  JS обработает переполнение (округлит на следующий месяц или вернёт
  `Invalid Date`) — оба случая дают несовпадение при раунд-трипе.
- **`isPlainObject` — общий приватный хелпер**, используется и в
  `validateRisk`, и в `validateRiskRecord`, чтобы не дублировать проверку
  `typeof value === 'object' && value !== null && !Array.isArray(value)`.

Регрессии не возникло: все существующие тесты используют `validRiskData()`,
которая всегда включает `status: 'open'`, поэтому ужесточение обязательности
статуса не сломало ни одного из 45 тестов первого раунда — добавлено ещё 19
новых, итог 64/64.

`tests.html` прогнан — 45 из 45 тестов пройдено, консоль чиста. Пользователь
не принял результат: независимая проверка нашла реальный пробел —
`validateRisk()` не годилась для проверки уже сохранённой записи
(`storage.js` шага 2), а на `null`/`undefined` бросала бы исключение.

**Раунд 2** (эта доработка): внесены точечные правки только в
`js/risk-model.js` и `js/tests/risk-model.test.js`, как и требовал промпт
(`tests.html` не потребовал изменений). Локальный сервер снова поднят
(`python3 -m http.server 8765`), `tests.html` открыт и прогнан в браузере
повторно: **64 из 64 тестов пройдено**, ни одного упавшего (45 прежних +
19 новых). Консоль браузера пуста — единственная запись это собственный
`console.log` со сводкой результатов. Сервер остановлен после проверки.

Закрыты все 3 требования из отказа: `validateRisk(null/undefined/строка/
массив)` возвращает `{ valid: false, ... }`, не бросая исключение;
отсутствующий и неизвестный статус теперь всегда ошибка (было — пропускался,
если `status` не передан); добавлена `validateRiskRecord()`, отклоняющая без
исключений: не-объект, отсутствующий/пустой `id`, неверный тип строковых
полей, неверные вероятность/влияние/статус, отсутствующие/неверного
типа/невалидные (в т. ч. семантически несуществующие, проверено раунд-трипом
через `Date`) ISO-даты, `updatedAt` раньше `createdAt`, сохранённые
`score`/`priority`. Все явно перечисленные в отказе тестовые случаи покрыты
(список — в разделе «Изменения в проекте» выше).

Формулировки сообщений об ошибках валидации в `SPEC.md` помечены как
«примеры», а не точный контракт — тексты в `risk-model.js` написаны по
их смыслу, но не всегда дословно совпадают. Это решение принято в рамках
обычной свободы реализации шага, не является продуктовым выбором,
требующим отдельного согласования — сообщения не зафиксированы в критериях
приёмки `SPEC.md` дословно.

Отдельно стоит иметь в виду на будущих шагах (не блокирует приёмку шага 1,
но влияет на дизайн шага 4): требование «статус всегда обязателен в
`validateRisk`» означает, что форма создания риска должна будет передавать
`status: 'open'` в объект перед вызовом `validateRisk`, а не полагаться на
то, что отсутствующий статус допустим по умолчанию.
