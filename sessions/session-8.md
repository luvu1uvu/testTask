## Размышления

**Структура рендера списка.** Выбрал таблицу (`<table>`) вместо карточек: реестр
из SPEC.md — табличная по природе сущность (несколько сопоставимых полей на
запись: вероятность, влияние, балл, приоритет, статус, мера, ответственный),
таблица даёт сравнение по столбцам без дополнительной вёрстки. Учёл, что при
~200 записях (ориентир из SPEC.md) таблица может быть шире вьюпорта — обернул
её в `.risk-table-wrapper` с `overflow-x: auto`, чтобы горизонтальную прокрутку
получала только сама таблица, а не вся страница (проверил через `scrollWidth`/
`clientWidth` в консоли: `body` не скроллится вбок, скроллится только обёртка).
Это заметил уже после первого визуального прогона — с первой версии CSS
последний столбец «Ответственный» просто обрезался без всякой прокрутки.

**Обработка повреждённых данных в `app.js`.** В плане шага 3 прямо сказано,
что UI-обработка повреждённых данных — не в объёме (шаг 6). Решение: если
`getAll()` возвращает `status !== 'ok'`, `app.js` трактует это как пустой
список для рендера (не бросает исключение, не подменяет и не удаляет данные
в `localStorage` — `resetStorage()` нигде не вызывается). Это временное
поведение до шага 6, явно прокомментировано в коде как таковое.

**Кнопка «Добавить первый риск» без обработчика.** По прямому указанию в
промпте — «не реализуй... рабочий обработчик кнопки добавления». Кнопка
существует, кликабельна визуально, но клик ничего не делает (обработчик не
навешан вовсе, а не навешан пустой noop) — это соответствует и PLAN.md
(«обработчик появится в шаге 4»), и прямому запрету пользователя добавлять
что-то за пределы шага 3.

**Тестовые данные и проверка сортировки.** Добавил 9 временных рисков через
`createRisk`/`addRisk`/`updateRisk` из консоли браузера (безопасный путь,
как и просил пользователь — не через прямую запись в `localStorage`).
Специально включил: балл 25 (границу «критический»), пару с одинаковым
баллом 15, но разным влиянием (5 и 3) — чтобы проверить второй уровень
компаратора; пару с одинаковым баллом 8 и одинаковым влиянием (4),
рассчитывая проверить третий уровень (`createdAt`) — но оба риска были
созданы в одном и том же браузерном тике и получили идентичный `createdAt`
до миллисекунды, поэтому фактически проверился не приоритет по дате, а
устойчивость сортировки при полном равенстве ключей (стабильный порядок
вставки сохранился — тоже корректное поведение). Это не рассматриваю как
дефект: сам компаратор `compareRisks` и тай-брейк по `createdAt` уже
покрыты отдельными модульными тестами шага 1 (`js/tests/risk-model.test.js`,
тест «compareRisks: при равном балле и влиянии выше более новый»), которые
управляют датами явно и проходят (97/97 в `tests.html`). Дублировать это в
ручной UI-проверке было бы избыточно и трудноуправляемо без задержки между
вызовами.

**Дважды перечитал критерий из PLAN.md** («Готово, когда…» шага 3) отдельно
от расширенного списка проверок из промпта пользователя (который шире
минимального критерия шага — включает явную проверку отсутствия закрытых/
реализовавшихся рисков и консоли) — выполнил оба.

## Понимание границ шага 3 и критерия «готово, когда…» (зафиксировано до начала правок)

**Входит в объём:**
- `index.html` — статический HTML-скелет страницы, подключение `js/app.js` как `<script type="module">`.
- `css/styles.css` — базовые стили страницы, списка рисков, меток приоритета (цвет + текст), пустого состояния, предупреждения о хранении.
- `js/ui/risk-list.js` — модуль рендеринга списка рисков в DOM: принимает массив рисков, для каждого вычисляет балл/приоритет через `calculateScore`/`getPriorityLevel`/`getPriorityLabel` из `risk-model.js` (не сохраняет их), получает русскую подпись статуса через `getStatusLabel`/`STATUS_LABELS`, отображает метку приоритета текстом и цветом (по CSS-классу от `getPriorityLevel`), рендерит пустое состояние (сообщение + кнопка «Добавить первый риск» без обработчика клика — обработчик появится в шаге 4).
- `js/app.js` — точка входа: при загрузке страницы читает риски через `storage.js` (`getAll()`/`load()`), фильтрует по умолчанию только активные статусы (`open`, `in_progress`, `monitoring`), сортирует через `compareRisks` из `risk-model.js`, передаёт результат в `risk-list.js` для рендера.
- Предупреждение о локальном хранении — статический текст в `index.html` или рендерится модулем, видимый без дополнительных действий пользователя.

**Не входит в объём (сознательно не реализуется в этом шаге):**
- Форма создания/редактирования риска.
- Рабочий обработчик клика по кнопке «Добавить первый риск» (кнопка есть визуально, клик ничего не делает).
- Переключатель/интерфейс фильтра по статусу (виден только фиксированный список активных статусов, без UI выбора).
- Удаление риска.
- UI-обработка повреждённых данных (сообщение «не удалось загрузить», кнопка сброса) — в этом шаге при повреждённых данных приемлемо не обрабатывать особый случай в интерфейсе, это отдельный шаг 6; проверять этот сценарий в рамках приёмки шага 3 не буду.

**Файлы, которые не трогаю:** `js/risk-model.js`, `js/storage.js`, `js/tests/*`, `tests.html`, `SPEC.md`, `PLAN.md`, `sessions/STATE.md`, `naive-run/`, `README.md`, `AGENTS.md`, `CLAUDE.md`.

**Критерий «готово, когда…» (дословно из PLAN.md, шаг 3):**
Страница открывается через `python3 -m http.server`; риски, добавленные вручную через `storage.js` в консоли браузера, отображаются отсортированными, с верными русскими подписями статуса и метками приоритета; при пустом хранилище видно сообщение и кнопку.

Дополнительно проверю (по прямому указанию в промпте пользователя, шире, чем минимальный критерий PLAN.md):
пустое хранилище; список с несколькими временными рисками разных баллов и статусов; правильность сортировки; русские подписи статусов; текстовые и цветовые метки приоритета; отсутствие закрытых/реализовавшихся в списке по умолчанию; отсутствие ошибок в консоли; побайтное восстановление продакшн-ключа после проверки.
