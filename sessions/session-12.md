**Техническая проблема: как сохранить PNG-доказательства на диск.** Инструмент
Browser-панели (`mcp__Claude_Browser__computer` с `action: "screenshot"`)
показывает результат только внутри диалога — не даёт прямого пути на диске
для сохранённого файла. Перебраны варианты: (1) поиск автосохранённых
скриншотов в `/private/tmp`, `~/Library/Caches`, кэшах Claude — ничего не
найдено; (2) headless Chrome через CLI-флаг `--screenshot=file.png` — даёт
файл, но это одноразовый снимок без возможности предварительно засеять
`localStorage` через реальные модули приложения перед снятием скриншота;
(3) попытка найти открытый порт удалённой отладки (CDP) самого Electron-
приложения Claude — не нашёл прослушиваемого TCP-порта, копаться в
внутренних unix-сокетах инструмента посчитал избыточным и нежелательным
вмешательством. Остановился на варианте (4): запустить свой собственный,
одноразовый headless-экземпляр уже установленного в системе Google Chrome
с явным `--remote-debugging-port` и чистым временным профилем (в
scratchpad-директории сессии, вне папки проекта), и написать минимальный
Python-клиент Chrome DevTools Protocol на голых сокетах (`cdp.py`, без
сторонних pip-пакетов — сознательно, чтобы не тянуть сетевые зависимости
через pip). Через этот клиент: `Page.navigate`, `Runtime.evaluate` с
`awaitPromise` (для динамического `import()` реальных ES-модулей
приложения и вызова `createRisk`/`addRisk`/`updateRisk`/`renderRiskList`),
`Page.captureScreenshot` → декодирование base64 → запись файла Python'ом.
Это дало полный контроль над содержимым скриншотов при сохранении полной
честности: скриншоты — снимки настоящего рендера настоящего кода
приложения, а не макеты. Решение зафиксировано и объяснено пользователю
в разделе «Методология проверки» `evidence/final-verification.md`, чтобы
не выглядеть как скрытая деталь.

**Порядок работы.** Основной интерактивный сценарий (создание, валидация,
статусы, фильтры, удаление, повреждённые данные, F5) прогнан целиком в
панели Browser — с реальными кликами и вводом текста через `computer`,
как и предполагает инструмент. Отдельно, через headless-Chrome-сессию,
досняты 4 обязательных PNG и проведён нагрузочный тест на 200 записях —
эти два вида проверки не пересекаются по данным (разные профили Chrome),
но используют один и тот же код приложения на одном и том же локальном
сервере `python3 -m http.server 8765`.

**Повторно столкнулся с известной проблемой из сессии 11** — первые клики
через инструмент автоматизации в панели Browser иногда не регистрировались
(кнопки «Изменить»/«Сохранить» не реагировали на клик по актуальным
координатам сразу после resize viewport). Как и в сессии 11, помогла
перезагрузка вкладки (`navigate` на тот же `index.html`) — после этого
клики снова обрабатывались штатно. Данные при этом не пострадали (клики,
которые «не сработали», действительно ничего не меняли — не было случая
тихого искажения состояния).

**Подбор распределения данных для нагрузочного теста.** Первая попытка
сформировать вероятность/влияние по формуле с двумя линейно зависимыми по
модулю 5 коэффициентами (`i*3 % 5` и `i*7+2 % 5`) дала на выходе только 2
уровня приоритета из 4 («низкий» и «критический») — совпадение вскрылось
после подсчёта фактического распределения (`byPriority`) и было видно на
самом скриншоте (монотонный блок одинаковых строк). Заменил на формулу
`вероятность = 1 + (i % 5)`, `влияние = 1 + (floor(i / 5) % 5)`, которая
детерминированно перебирает все 25 комбинаций — получил распределение
«низкий» 64 / «средний» 56 / «высокий» 48 / «критический» 32, все четыре
уровня видны одновременно на итоговом скриншоте.

**Ошибка при первой попытке проверить отзывчивость интерфейса на 200
записях.** Первый вызов клика «Изменить» после ручных измерений
производительности вернул форму без данных (`hasForm: false`) — причина:
измерения сортировки/фильтра сами вызывали `renderRiskList()` напрямую с
заглушками-колбэками (`onEdit: () => {}`), тем самым подменяя в DOM
настоящие обработчики кликов, привязанные `app.js`. Клик «Изменить» после
этого вызывал пустую заглушку, а не настоящий переход к форме. Исправил,
перезагрузив страницу (`Page.navigate`) перед проверкой клика — на
странице, отрисованной настоящим `app.js`, клик открыл форму с реальными
данными риска («Тестовый риск №199…») ожидаемо.
