## Размышления

Перед планированием перечитаны `AGENTS.md` (Часть I и II), `SPEC.md` целиком
и `sessions/STATE.md`. Противоречий между `SPEC.md` и Частью II `AGENTS.md`
не найдено — уточняющий вопрос пользователю в этой сессии не потребовался.

Ключевое решение — как бить работу на шаги:

- Часть II `AGENTS.md` явно требует разделять код на 4 области ответственности
  (расчёты и валидация; хранение данных; интерфейс; запуск приложения) и
  проверять расчёты/валидацию и хранение через `tests.html` на тех же
  экспортируемых функциях, что использует приложение. Это напрямую подсказывает
  первые два шага плана: сначала чистая бизнес-логика (`risk-model.js`) без
  DOM и localStorage, затем хранение (`storage.js`) — оба полностью
  покрываемые модульными тестами без браузерного UI. Это соответствует
  явному требованию «сначала фундамент и проверяемая логика, затем интерфейс».
- Формула балла/приоритета, компаратор сортировки (балл → влияние → новизна)
  и правила валидации (длины полей, обязательность меры/ответственного при
  переводе в «В работе», допустимые значения 1–5) — всё это чистые функции без
  побочных эффектов, поэтому отнесены к `risk-model.js`, а не к интерфейсу.
  Это позволяет закрыть числовые пограничные случаи из критериев приёмки
  (балл 25/критический, границы 4/5/9/10/15/16) уже на первом шаге, юнит-тестами,
  до появления UI.
- UI решил не делать одним шагом целиком, а разбить на 4 отдельных шага
  (каркас + список, форма создания/редактирования, статусы + фильтры,
  удаление + обработка повреждённых данных), потому что иначе один шаг вышел
  бы непропорционально большим и трудно проверяемым «одним вызовом агента»,
  а правило требует, чтобы каждый шаг закрывался проверяемым критерием
  «готово, когда…». Разбиение по этим границам совпадает с естественными
  группами критериев приёмки в `SPEC.md` (пустой реестр/сортировка/приоритет →
  валидация формы → статусы/фильтры → удаление/повреждённые данные), поэтому
  каждый шаг закрывает связный, а не произвольный набор пунктов.
- Отдельно вынес финальную комплексную проверку (полный чек-лист критериев
  приёмки, проверка на ~200 записях, чек-лист «Что проверить перед финальным
  ответом» из `AGENTS.md`) в последний, седьмой шаг — по прямому требованию
  промпта не смешивать её с реализацией.
- `README.md` с итоговым отчётом, сравнение с `naive-run/` и независимый аудит
  сознательно не включены в этот план — по прямому указанию промпта они
  логичнее как отдельные последующие этапы (сессии) после того, как
  реализация принята.
- Проверил, что план не предполагает изменения `naive-run/`, Части I
  `AGENTS.md` или полной перезаписи `SPEC.md` — все шаги создают только новые
  файлы приложения и тестов и точечно обновляют `sessions/STATE.md` по итогам
  каждого шага (это не запрещено правилами).
- Сомнение, которое не потребовало отдельного вопроса пользователю: разбивать
  ли модуль «интерфейс» на несколько файлов (список, форма, диалоги, фильтры)
  или держать один `ui.js`. Часть II `AGENTS.md` требует «один модуль — одна
  область», но не запрещает несколько файлов внутри одной области. Решил не
  фиксировать это жёстко в плане — точное разбиение файлов интерфейса решается
  на этапе выполнения соответствующего шага, план называет вероятные файлы
  как ориентир, а не как обязательство.

Первая версия плана (7 шагов) была показана в чате и не согласована —
пользователь вернул её с семью конкретными замечаниями. Ключевые решения при
переработке:

- **Статус риска как значение хранения.** Пользователь зафиксировал точную
  форму хранения (`{ version, risks }`, ключ, id/createdAt/updatedAt, балл не
  хранится), но не уточнил явно, в каком виде хранится поле `status` —
  как русская строка («Открыт» и т. д.) или как внутренний код на английском
  с отдельной картой подписей. Это не подпадает под явные пункты «обязан
  остановиться» из `AGENTS.md` (структура/формат ещё не были согласованы
  целиком до этого сообщения — они согласуются прямо сейчас, значит это не
  «изменение» уже согласованного формата) и не критично/необратимо на этапе
  плана. Принял решение хранить статус ровно теми русскими строками, что
  использует `SPEC.md» («Открыт», «В работе», «Под наблюдением»,
  «Реализовался», «Закрыт») — без отдельной кодовой карты, так как
  локализация не планируется никогда (см. «Допущения» в `SPEC.md`: язык
  интерфейса русский без переключения), а лишний слой code↔label создал бы
  риск рассинхронизации без реальной пользы. Решение явно вынесено в план
  как проверяемое пользователем допущение, а не скрыто внутри реализации.
- **Генерация id.** Для стабильного уникального `id` выбран `crypto.randomUUID()`
  — нативный Web Crypto API браузера (не внешняя библиотека, не CDN,
  доступен в защищённом контексте, а `localhost` браузеры считают защищённым
  контекстом даже по HTTP, так что `python3 -m http.server` подходит). Это
  соответствует стеку («чистый ES2020+, без сборки и библиотек»).
- **Атомарность проверки повреждённых данных.** Пользователь попросил
  зафиксировать реакцию на неподдерживаемую версию как «столь же безопасную»,
  как на повреждённый формат — по аналогии решил, что storage.js проверяет
  форму целиком (версия + структура + для каждого риска проходит валидацию
  модели из шага 1) и при любом несоответствии считает **весь** набор данных
  повреждённым, без попытки частичного восстановления отдельных записей.
  Частичное восстановление прямо запрещено `SPEC.md` («восстановление,
  исправление... повреждённых данных — вне v1»), так что более гранулярная
  логика была бы лишней сложностью без пользы. Решение зафиксировано в шаге 2
  как явное допущение.
- **Изоляция тестов хранилища.** Чтобы тесты `storage.js` не трогали
  продакшн-ключ `project-risk-tracker:v1`, выбран самый простой вариант,
  не требующий отдельного класса-адаптера: экспортируемые функции принимают
  необязательный параметр ключа хранения (по умолчанию — продакшн-ключ),
  тесты всегда передают отдельный тестовый ключ и удаляют его по завершении
  каждого теста. Это проще, чем полноценный объект-адаптер, и не противоречит
  требованию пользователя («ключ либо адаптер» — выбран ключ).
- **Разделение «пустой реестр» vs «пустой результат фильтра».** Перечитал
  `SPEC.md` ещё раз и явно развёл в плане два разных пустых состояния:
  полностью пустой реестр (0 записей вообще, шаги 3–4, есть кнопка «Добавить
  первый риск») и пустой результат текущего фильтра при непустом реестре
  (шаг 5, нет этой кнопки, есть «Сбросить фильтры»). Это ровно то различие,
  которое пользователь отметил как потерянное в первой версии плана —
  добавил его как отдельный явный пункт «готово, когда» в шаге 5 и шаге 6
  (сценарий: фильтр непустой, удаление последнего видимого в нём риска не
  должно ошибочно показать состояние «реестр пуст», если в хранилище остались
  риски других статусов).
- **Файлы для статусов и фильтров (замечание 3).** Убрал развилку
  «risk-form.js или status.js» — управление статусом (включая блокировку
  перехода в «В работе» без меры/ответственного) переносится в существующий
  `js/ui/risk-form.js`, потому что смена статуса — часть той же формы
  редактирования риска и использует те же валидаторы из шага 1. Отдельный
